# 发布流程规格

本文件描述版本号、变更记录与发布说明的维护方式。这些环节此前没有测试覆盖，
曾导致连续九个版本的发布说明为空而未被发现——流水线显示成功，页面却是空的。

## 版本号一致性

`VERSION` 是唯一真相源，另外两处包元数据必须与它保持一致。三处分离是各生态工具链的
要求，但对外只应存在一个版本号。

不一致的后果是静默的：构建产物、更新检查与发布标签会各自报告不同的版本，
而没有任何一处会报错。

- **AC-REL-001-01**：`VERSION`、`backend/pyproject.toml` 与 `frontend/package.json`
  中的版本号必须一致。

## 发布说明提取

发布说明由 `CHANGELOG.md` 的对应小节生成，避免手工维护两份内容。提取由
`scripts/extract_changelog.py` 承担，CI 在打标签时调用。

标题行本身不进入发布说明，因为发布页面已用标签名作为标题，重复显示没有意义。
提取结果也不应带首尾空行，否则发布页会出现多余留白。

版本号接受带或不带 `v` 前缀两种写法：标签名带前缀，而小节标题在历史上写法并不统一，
调用方不应承担规范化责任。

最关键的是失败语义。小节缺失时必须明确失败：此前的实现静默产出空文件，
于是连续九个版本发布了空说明，而流水线仍然报告成功。

- **AC-REL-002-01**：提取结果不得包含版本标题行本身。
- **AC-REL-002-02**：提取结果不得包含首尾空行。
- **AC-REL-002-03**：版本号带或不带 `v` 前缀都必须能被识别。
- **AC-REL-002-04**：遇到下一个版本标题时必须停止，不得混入后续版本的内容。
- **AC-REL-002-05**：小节缺失时必须以非零退出码失败，不得输出空内容或静默成功。

## 发布说明修复

历史发布可能因提取缺陷而缺少说明，因此需要能事后补齐的工具
（`scripts/sync_release_notes.py`）。它连接远端 API，属于人工执行的一次性修复手段，
不参与常规发布流程。

该工具默认只填充空说明。手工撰写的说明是人的判断，工具不应覆盖它——否则一次误用
就会丢掉人工内容，且无法恢复。

- **AC-REL-003-01**：同步工具默认只填充空说明，不得覆盖已有内容。
- **AC-REL-003-02**：同步工具必须支持不写入任何数据的预演模式。

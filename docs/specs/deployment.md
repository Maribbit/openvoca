# 部署与分发规格（公网 VPS 方案，已搁置）

> **本文件已搁置。**
>
> 它描述的是面向公网 VPS 的部署方案：反向代理、TLS 终结、镜像仓库、CI 构建与访问控制。
> 当前的实际部署目标是自有机器 + 私有网络，对应规格见 [`private-deployment.md`](./private-deployment.md)，
> **以那份文档为准**。
>
> 保留本文件的原因有两点：一是其中的核心不变量（差异只允许出现在装配层）对两种部署同样成立，
> 私有规格正是建立在它之上；二是若将来确实需要公网暴露，访问控制一节（`AC-DEPLOY-003-*`）
> 会立即成为硬前提，届时无需重新推导。
>
> 本文件的验收标准仍列在 `deferred.txt` 中，状态是「已定义、已搁置、未实现」，
> 不属于当前工作项。

本文件描述 OpenVoca 在「本机打包」与「服务器部署」两种分发方式下如何共用同一份应用代码，
以及部署专属能力的边界。它不规定具体的主机、域名或云厂商。

## 分发一致性（核心不变量）

两种分发方式的差异只允许出现在**装配层**（谁准备文件、谁启动进程、谁做反向代理），
不允许出现在应用逻辑里。`scripts/bundle.py` 是装配器而非应用的一层：它不包裹、不修改应用代码，
应用也不知道自己是被打包运行还是被容器运行。

应用只依赖以下布局契约，两种分发必须各自满足：

- **进程**：`python -m uvicorn src.main:app`，工作目录为 `backend/`。
- **静态资源**：相对应用文件解析出的 `frontend/dist`。
- **数据**：`OPENVOCA_DATA_DIR` 指向的目录下的 `openvoca.db`。
- **版本**：`OPENVOCA_VERSION` 环境变量，运行时读取。
- **词典**：`backend/data/dictionary.db`。
- **用户配置**：provider 端点、模型、密钥等只存在于 SQLite 设置表，不来自环境变量。

由此得出两条硬性约束：

- 静态资源必须由应用自身提供。不得为部署引入第二个静态服务器（例如用反向代理直接托管 `dist`），
  否则 SPA 回退逻辑会出现两套实现，其中一套永不经过真实流量。
- 不得引入基于环境变量的 provider 配置。provider 的唯一真相源是设置表（见 `provider-generation.md`），
  双真相源会互相覆盖。

部署专属能力必须 opt-in 且默认关闭，使本机打包不需要为部署特性做任何维护。

- **AC-DEPLOY-001-01**：未设置任何部署专属环境变量时，应用必须保持与本机运行一致的行为：全部现有接口免认证可访问，且响应内容不变。
- **AC-DEPLOY-001-02**：静态资源目录必须相对于应用文件解析，不得依赖进程工作目录。

## 启动可见性

静默失败是最难排查的部署故障：路径不对时接口照常返回健康，只有界面白屏。
因此关键路径必须在启动时可见。

数据库路径部分由 `private-deployment.md` 的 `AC-PRIV-002-05` 承担，本文件只保留静态资源部分。

- **AC-DEPLOY-002-01**：启动时必须输出实际使用的静态资源目录。
- **AC-DEPLOY-002-02**：静态资源目录缺失时，启动必须输出明确警告，而不是静默跳过静态路由。

## 访问控制

认证是可选能力，默认关闭；开启后覆盖除健康检查外的全部请求，包含静态资源。

机制为**会话 Cookie**，不得要求自定义请求头。选择 Cookie 而非 HTTP Basic 的原因：

- 手机使用需要真正的登录页与登出。Basic 依赖浏览器原生弹窗，无法登出，只能清空浏览器缓存。
- 朗读通过 `new Audio(url)` 播放，并依赖渐进式流式播放（边下边播，长句不必等整段下载完）。
  `new Audio` 无法附加自定义请求头；若改为先 `fetch` 取回整段音频再播放，会失去渐进播放体验。
- 流式生成虽使用 `fetch` 且可附加请求头，但音频路径无法统一，混用两套凭据传递方式会提高维护成本。

会话状态存放在 Cookie 内并由密钥签名，不使用服务端会话存储。这个选择的首要目的是**让会话在服务重启后依然有效**：
本机与容器部署都会频繁重启进程（改配置、重新部署、VPS 重启），若每次重启都强制在手机上重新登录，
日常可用性会明显下降。

由此产生一条实现约束：签名密钥必须跨重启稳定。若密钥在每次启动时随机生成，签名 Cookie 会退化为进程内会话，
失去选择它的全部意义。密钥由单一环境变量（登录密码）派生，不引入独立的密钥变量：少一个需要长期保管的秘密，
且「改密码即全部登出」在单用户场景下正是期望行为。

代价是服务端无法单独吊销某个会话。单用户场景下这几乎无实际影响：需要强制登出时轮换凭据或密钥即可，
轮换会使全部既有会话立即失效。

认证只在 TLS 之后才有意义：会话凭据在明文 HTTP 下等同于公开。反向代理负责终结 TLS，
应用监听内部网络，不直接暴露端口。应用位于 TLS 终结之后时，还需能识别上游转发的协议，
否则无法安全地为 Cookie 设置 `Secure`。

不得为了跨源访问放宽 CORS。当前为同源部署，不需要 CORS。缺少 CORS 响应头时，
浏览器会在预检阶段拒绝跨源 JSON 请求，请求根本不会到达应用，这层保护是免费的。

- **AC-DEPLOY-003-01**：未配置认证凭据时，所有接口保持免认证访问。
- **AC-DEPLOY-003-02**：配置认证凭据后，未携带有效凭据的请求必须被拒绝，且不得返回任何业务数据，包含静态资源。
- **AC-DEPLOY-003-03**：健康检查接口必须始终免认证，供编排器与反向代理探活。
- **AC-DEPLOY-003-04**：认证必须使用会话 Cookie，使音频播放与流式生成无需前端附加自定义请求头即可工作。
- **AC-DEPLOY-003-05**：会话 Cookie 必须设置 HttpOnly 与 SameSite，不得允许前端脚本读取。
- **AC-DEPLOY-003-06**：必须提供登录与登出入口；登出后浏览器不得再携带有效会话凭据。
- **AC-DEPLOY-003-07**：会话在服务重启后必须保持有效；签名密钥不得在每次启动时重新生成。
- **AC-DEPLOY-003-08**：会话有效期为 30 天，且必须由服务端在签名载荷内校验，不得仅依赖 Cookie 的过期时间。
- **AC-DEPLOY-003-09**：登录失败必须节流；同一来源连续失败达到阈值后，后续尝试必须被拒绝或显著延迟。
- **AC-DEPLOY-003-10**：节流只作用于登录端点，不得阻断已认证会话的请求。

会话有效期必须由服务端校验而非仅依赖 Cookie 的过期时间：Cookie 的 `Max-Age` 只是对客户端的请求，
持有凭据的一方可随时改写它。若有效期不在签名载荷内，被盗的凭据可以被无限期续命。

登录端点会持续暴露在自动化扫描之下，节流是必要条件但不足以单独承担防护：单密码认证没有天然的尝试次数上限，
而节流通常只提高单次尝试的成本。因此密码本身必须是长且随机的，两者叠加才构成实际防护。

反向代理层不承担认证。它只负责终结 TLS 与转发，认证完全由应用自身提供，避免两级认证导致重复登录。
后续如需外层限制，可使用 Cloudflare Access 这类在应用之前生效的方案；它同样不与应用认证冲突，
且能额外提供限流与阻挡扫描器的能力。

## 暴露面收敛

`GET /api/settings` 是通用设置读取接口，会原样回传整个 `provider` namespace，包含明文密钥。
这是一条独立于部署的设置接口缺陷，规格归属 `settings-shell.md`（见 `AC-SET-004-01` 与密钥存储一节）；
在此记录是因为它必须在公网暴露前修复，且与认证正交——即使开启了认证，密钥也不该出现在通用读取路径上。

## 版本与更新

以下两条与部署环境无关，私有网络部署同样受其约束，因此未在 `private-deployment.md` 另立标准。

- **AC-DEPLOY-005-01**：必须能通过 `OPENVOCA_VERSION` 注入版本号，且更新检查接口回传该值。
- **AC-DEPLOY-005-02**：未设置 `OPENVOCA_VERSION` 时，更新检查必须安全跳过且不影响其他接口。

容器部署下更新语义与本机打包不同：界面上的更新提示指向新的发布版本，而容器更新需要拉取新镜像。
这不影响上述接口行为，但需要在部署文档中说明，避免误导。

## 数据存储

单用户场景下 SQLite 足够日常使用，不需要为此引入数据库服务：写入来自用户手动操作而非并发流量，
且字典库是只读的。需要关注的是**数据可恢复性**而非吞吐量。

当前实现使用默认的连接池与回滚日志模式，未做任何 PRAGMA 调优。这在单用户下不构成问题，
但下列事实必须被记录，以便备份与恢复时不会犯错：

- SQLite 数据库不是单文件。回滚日志模式下写入期间会存在 `-journal` 文件，直接复制主文件可能得到损坏或过期副本。
- 备份必须在数据库无写入时进行，或使用 SQLite 自身的备份机制，而不是文件复制。

应用在运行期只写入数据库文件，不产生其他持久化状态。词典库只读，且随镜像分发，不需要备份。
cooldown 是学习轮次计数而非时间间隔，因此算法不依赖时区或系统时钟的绝对时间，
服务器时区设置不影响学习进度。

### 备份策略

备份暂不实现，依赖界面内的导出功能作为唯一恢复手段。选择这一策略的前提是：VPS 整体损坏属于低频事件，
而手动导出不需要登录服务器，是成本最低的方式。

需要明确该策略的覆盖范围与缺口：

- 词条导出（CSV）覆盖全部词条字段，包含熟悉度、cooldown、上下文、出现次数与时间戳。
- **但词条导出不包含任何设置。** 界面语言、主题、缩放、选词数量、词典语言、provider 端点与模型
  都不在 CSV 中，需要另行导出设置 JSON。
- 设置导出按设计排除 provider API key，因此恢复后必须手动重新填写密钥。
- 导出操作依赖应用正在运行。服务器完全不可访问时，只能依赖此前已下载的导出文件。

因此「仅靠 CSV」不足以恢复可用状态，实际需要词条 CSV 与设置 JSON 两份导出，外加重新填写 API key。

## 部署环境

目标环境是单台 VPS 上的两个容器：应用容器与反向代理容器。应用不映射到宿主机端口，
仅代理容器暴露 80/443，两者通过 Docker 内部网络通信。

不引入容器编排系统。编排的核心价值在于跨节点调度与节点故障自愈，而单台机器上不存在可调度或可接管的目标，
自愈能力在逻辑上落空；其控制平面的常驻开销反而可能超过应用本身。声明式期望状态可由 compose 满足。

反向代理需要域名才能签发证书，这是部署的硬性前提。若没有域名，只能退化为自签证书或明文访问，
而明文访问会使会话凭据失去保护。

域名的备案状态与托管位置无关。ICP 备案只对位于中国大陆境内的服务器提出要求，境外托管不需要备案，
已有的备案也不会阻止域名指向境外服务器。可能的副作用是原接入商在发现域名不再指向其服务器后注销网站备案；
这不影响境外使用，但若将来迁回境内托管，需要重新办理接入。

镜像在 CI 中构建并推送到镜像仓库，VPS 只负责拉取。这既避免在 VPS 上安装完整构建工具链，
也避免在资源受限的机器上编译依赖，同时与既有的多平台发布流程共用同一条流水线。

## 运行时注意事项

以下事实不落为验收标准，但会直接影响部署是否可用：

- 应用必须监听所有网络接口，否则同一 Docker 网络内的反向代理无法访问它。
- 容器日志默认无限增长，需要限制单文件大小与保留数量，否则会静默占满磁盘。
- 数据目录需要与容器运行用户匹配的写权限，否则应用启动即失败。
- 镜像构建上下文需要排除依赖目录与构建产物，否则每次构建都会传输数百 MB 无用数据。

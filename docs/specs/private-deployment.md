# 私有网络部署规格

本文件描述在**自有机器 + 私有网络**上部署 OpenVoca 的方式，目标场景是单用户
（部署者本人）在家中长期开机的机器上运行服务，供自己在外随时学习与复习。

它与 `deployment.md` 共享同一条核心不变量（应用不知道自己在被怎样运行），但两者面向的
环境不同，因此结论也不同。`deployment.md` 面向公网 VPS，需要反向代理、TLS 终结、镜像仓库
与访问控制；本文件面向私有网络，这些约束大部分消失。**当前以本文件为准，VPS 方案搁置。**

## 目标环境与威胁模型

单台自有机器，长期开机，通过私有网络访问。部署者是唯一的用户，也是唯一的管理员。

由此得出三条与环境相关的结论：

- **没有匿名流量。** 能到达服务的人默认已通过私有网络的设备认证。这消掉了一整类问题：
  端口扫描、登录端点爆破、爬虫、以及为抵御它们而必需的节流机制。
- **不需要应用层 TLS。** 覆盖网络（WireGuard / Tailscale 一类）在网络层加密，应用再加一层
  TLS 是重复的。若改用普通局域网明文访问，则需接受同网段可嗅探，这是部署者自己的取舍，
  不由本规格强制。
- **不需要为扩展性做任何设计。** 单用户、单进程、读写都来自手动操作。任何为吞吐量或高可用
  引入的组件都是净负债。

需要真正解决的问题只有**更新**：代码更新频繁，而每次手动重新部署的成本会累积成不去更新的理由。
因此本规格的绝大部分内容是关于「怎样让更新变便宜且不丢数据」，而不是关于怎样把服务跑起来。

## 部署形态

选择 **git 检出 + `uv sync`**，不使用 `scripts/bundle.py` 的产物。

bundle 的全部价值在于「目标机器无需预装 Python 与 Node」，而自有机器上这个前提不必要。
更关键的是它做不到：`PLATFORM_TAG` 取自构建机，在 macOS 上构建出的包不能运行在 Ubuntu x86_64 上，
所以跨平台构建反而需要额外机器或 CI。git 方案下版本就是标签，回滚就是检出旧标签，
不需要 CI、不需要镜像仓库、也不需要把构建产物当作长期维护的对象。

两个部署形态仍需共用同一份应用代码。应用侧只依赖以下契约，与 `deployment.md` 一致：

- **数据**：`OPENVOCA_DATA_DIR` 指向的目录下的 `openvoca.db`。
- **版本**：`OPENVOCA_VERSION` 环境变量。
- **用户配置**：provider 端点、模型与密钥只存在于 SQLite 设置表，不来自环境变量。
- **静态资源**：由应用自身提供，不引入第二个静态服务器。

## 代码与数据分离

这是让更新变便宜的前提，也是唯一必须先做的事。更新在本质上只有三个动作：
**换代码、重启进程、数据原地不动**。若数据位于代码目录内，第一个动作就会删掉数据，
于是任何更新方案都不成立。当前 bundle 的启动器正是这种形态：它把数据目录固定为包内的
`data/`，并用 `{**os.environ, "OPENVOCA_DATA_DIR": ...}` 强制覆盖，外部设置被静默忽略。

因此数据目录必须是一个**独立于代码修订的固定路径**（例如 `/var/lib/openvoca`），
代码目录则是可整体替换的。这个划分一旦建立，更新方案长什么样、由什么触发，都不再影响正确性：
脚本、定时器、网页按钮最终都在执行同一个原语。

- **AC-PRIV-001-01**：应用必须从 `OPENVOCA_DATA_DIR` 解析数据目录；未设置时回退到进程工作目录，使本机开发行为不变。
- **AC-PRIV-001-02**：启动器不得覆盖调用方已设置的 `OPENVOCA_DATA_DIR`。
- **AC-PRIV-001-03**：应用在运行期只写入数据目录，不得写入代码目录或进程工作目录。
- **AC-PRIV-001-04**：数据目录路径必须独立于代码修订；切换修订不得改变该路径。

## 启动期模式自检

`SQLModel.metadata.create_all()` 只创建缺失的**表**，对已存在的表不做任何改动。
因此给 `WordRecord` 增加一个字段后：应用能启动、健康检查返回 200、静态页面正常加载，
而第一次查询该表时才会失败。故障不是「起不来」，而是「看起来正常，一用就错」——
这是最难排查的一类，因为所有自动化探活都报告健康。

正确性不能依赖「记得手写迁移」。自检必须**失败即拒绝启动**：宁可服务不可用且原因明确，
也不要服务可用但数据路径错误。

- **AC-PRIV-002-01**：启动时必须核对数据库中实际存在的列与模型声明的列一致。
- **AC-PRIV-002-02**：核对不通过时必须以非零状态退出，且不得开始接受请求。
- **AC-PRIV-002-03**：失败信息必须指明不一致的表名与列名。
- **AC-PRIV-002-04**：模式一致时必须正常启动，不得产生误报。
- **AC-PRIV-002-05**：启动时必须输出解析后的数据目录与数据库路径。

## 部署的原子性

部署脚本的不稳定来源是**聪明**。一旦脚本开始解析版本号、判断是否需要迁移、决定要不要回滚，
它就会随着应用演化不断失配，而这些逻辑无法被单独测试。本规格的纪律不是「不写脚本」，
而是**脚本不许知道任何事**：它只负责搬运不透明的产物、做快照、切换、重启。

职责三层切分，各自只处理自己懂的部分：

| 层 | 负责 | 明确不负责 |
|---|---|---|
| 部署脚本 | 搬运代码、快照数据库、切换软链、重启服务 | 版本判断、模式逻辑、条件分支 |
| 应用 | 模式一致性自检，不一致则拒绝启动 | 不知道自己在被部署 |
| 服务管理器 | 进程监督、崩溃重启、固定环境变量 | 不理解应用语义 |

切换必须通过替换符号链接完成，而不是就地覆盖。就地覆盖会产生一个「一半新一半旧」的窗口，
而重启可能落在这个窗口内；软链接替换是原子操作，窗口不存在。

快照必须使用 SQLite 自身的备份机制（备份 API 或 `VACUUM INTO`），不得复制文件：
回滚日志模式下写入期间存在 `-journal` 旁文件，直接复制主文件可能得到损坏或过期的副本。
快照是唯一能把「某次更新搞丢了数据」降级为无事发生的措施，而脚本恰好是唯一知道更新即将发生的一层。

- **AC-PRIV-003-01**：部署必须是一条命令且只接受目标修订号，不得包含版本判断、迁移决策或条件分支。
- **AC-PRIV-003-02**：代码切换必须通过替换符号链接完成，不得就地覆盖正在服务的目录。
- **AC-PRIV-003-03**：切换前必须对数据库做快照，且必须使用 SQLite 自身的备份机制而非文件复制。
- **AC-PRIV-003-04**：任一步骤失败时必须以非零状态退出，并保持上一修订继续服务。
- **AC-PRIV-003-05**：部署失败时不得留下半切换状态。
- **AC-PRIV-003-06**：运行中的修订号必须可以从应用观察到。

## 进程监督

服务需要长期无人值守运行，因此需要进程监督而非手工启动：崩溃后自动重启、主机重启后自动恢复。
这部分交给系统服务管理器，不自己实现守护逻辑。

反向代理是可选的。私有网络内直接访问应用端口即可；只有在需要域名或统一入口时才引入代理，
且代理不承担认证——认证在私有部署中由网络层完成。

- **AC-PRIV-004-01**：进程异常退出后必须被自动重启。
- **AC-PRIV-004-02**：主机重启后必须自动恢复服务。
- **AC-PRIV-004-03**：监听地址与端口必须可配置，以便私有网络内访问。
- **AC-PRIV-004-04**：应用不得承担 TLS 终结。
- **AC-PRIV-004-05**：健康检查接口必须可用于探活。

## 更新请求与执行分离

界面内的更新提示目前只是**通知器**：它能告知有新版本，但没有任何执行路径。
把它变成一键升级需要一个前提，而这个前提决定了它必须最后做。

自举悖论：执行更新的进程正是要被替换的进程。它要么杀掉正在返回 HTTP 响应的自己，
要么派生一个脱离的辅助进程。若切换只完成一半而应用起不来，**恢复用的界面就是刚刚死掉的应用**，
于是只能登录服务器手工修复——也就是说，这个功能的失败模式恰好就是它想消除的那个场景。

安全的形态是：应用可以**请求**更新、可以**展示**结果，但不能**执行**更新。
具体做法不需要提权：应用向数据目录写入一个请求文件，服务管理器的 path 单元（或定时器）
观察到后以独立单元运行更新器，把结果写入结果文件，应用读出来展示。
失败于是退化为「按钮没反应，日志里说明了原因」，而不是「应用把自己删了」。

这一节记录的是设计边界而非当前工作项。在进程监督落地之前不应开始实现。

- **AC-PRIV-005-01**：应用不得直接执行自身更新，只能发出更新请求。
- **AC-PRIV-005-02**：更新请求必须由独立于应用的服务单元执行。
- **AC-PRIV-005-03**：更新结果与失败原因必须可被应用读取并展示。

## 明确排除的做法

以下做法在评估后不采用，记录理由以免反复讨论：

- **CI 通过 SSH 推送到家庭网络。** 它要求把一个能进入私有网络的私钥长期存放在 CI 的 secret 中，
  而换来的收益只是省掉一条本地命令。私有网络的凭据不应离开私有网络。
- **运行时自更新。** 理由见上一节的自举悖论。
- **公网暴露。** 若将来确需公网访问，`deployment.md` 的访问控制一节（`AC-DEPLOY-003-*`）
  全部条款立即成为硬前提，因为设置表内包含 provider 密钥。在私有网络下这些条款不适用。
- **容器编排。** 单台机器上不存在可调度或可接管的目标，声明式期望状态由服务管理器即可满足。

## 与 deployment.md 的关系

`deployment.md` 保留为公网 VPS 方案，当前搁置。两者的分工：

- **共同的不变量**：应用不知道自己在被怎样运行；差异只允许出现在装配层。
- **本文件取代** `deployment.md` 在私有部署场景下的全部适用性。
- `AC-DEPLOY-002-01` 中的数据库路径部分由本文件的 `AC-PRIV-002-05` 承担，
  前者只保留静态资源部分。
- `AC-DEPLOY-005-01` 与 `AC-DEPLOY-005-02`（版本注入与未设置时的安全跳过）与部署环境无关，
  私有部署同样受其约束，因此不在本文件另立标准。

## 待定项

以下问题在实现前需要确认：

- 代码分发方式：SSH 手动执行，或裸仓库配合 `post-receive` 钩子。两者都复用已有的 git，
  不引入新的秘密；区别只在于是否需要从开发机发起连接。
- 是否引入私有覆盖网络（Tailscale / WireGuard 一类）。它消掉暴露面与登录摩擦，
  代价是每台客户端需要安装并加入网络。
